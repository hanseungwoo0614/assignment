# 학생 구현 및 제출 상세 체크리스트

프론트 1종과 백엔드 1종만 선택합니다. 각 항목은 직접 확인한 뒤 체크하세요. 제공 코드는 CRUD까지 동작하며 인증 TODO가 남아 있습니다. 완료 기준은 공지문과 공통 API 명세이고, AI 활용 여부와 관계없이 같습니다.

## 1 실행 준비와 제공 코드 이해

- [ ] 주제, 대상 사용자, 선택 기술 조합을 정했다.
- [ ] 선택한 백엔드 README의 의존성 설치와 실행을 완료했다.
- [ ] GET /api/health → HTTP 200, status: ok를 확인했다.
- [ ] 프론트에서 등록·목록·상세·수정·삭제를 직접 실행했다.
- [ ] 화면 → api.js → 라우트 → 인증 함수 → 저장소의 호출 흐름을 찾았다.
- [ ] 올바른 로그인에서 시작 코드의 501 NOT_IMPLEMENTED를 확인하고 구현 위치를 찾았다.
- [ ] 데모 사용자 ID 반환, 빈 작성자 검사, 항상 true인 canEdit를 찾았다.

## 2 BE-01 서버 설정과 로그인

Express는 src/auth.js, FastAPI는 auth.py, Spring은 src/main/java/edu/classroom/board/AuthService.java를 수정합니다. 설정·라우트 등 관련 파일도 필요하면 수정하세요.

- [ ] JWT_SECRET을 새 난수로 설정하고 64자리 hex를 32바이트 키로 사용한다.
- [ ] 빈 키, 잘못된 형식, 제공 예시 키를 최종 서버에서 거부한다.
- [ ] .env 또는 환경변수가 실제 서버 프로세스에 전달되는지 확인했다. Spring은 .env를 자동으로 읽지 않는다.
- [ ] 제공한 비밀번호 검증을 유지하고 계정 확인이 끝난 사용자에만 발급한다.
- [ ] issueToken / issue_token의 501 임시 구현을 제거했다.
- [ ] HS256으로 발급하며 sub는 문자열 사용자 ID, exp는 UTC Unix 초이다.
- [ ] iss=webservice-class, aud=board-api와 기본 TTL=90초를 반영한다.
- [ ] 토큰과 사용자 응답에 비밀번호·해시·서버 키가 없다.
- [ ] 정상 로그인은 200과 accessToken·expiresIn·user를 반환한다.
- [ ] 비밀번호 오류·없는 계정은 401 INVALID_CREDENTIALS, 형식 오류는 400 BAD_INPUT이다.

## 3 BE-02 모든 보호 API의 인증

대상은 GET /api/me, POST /api/posts, PUT /api/posts/{id}, DELETE /api/posts/{id}입니다.

- [ ] currentUserId / current_user_id의 데모 ID 반환을 제거했다.
- [ ] 토큰 없음·Bearer 헤더 형식 오류는 401 TOKEN_REQUIRED이다.
- [ ] 허용 알고리즘을 HS256으로 고정하고 서명을 검증한다.
- [ ] exp·iss·aud·sub의 존재·값·형식과 만료를 검증한다.
- [ ] decode만으로 사용자 ID를 신뢰하지 않는다.
- [ ] 변조·잘못된 클레임·없는 사용자는 401 INVALID_TOKEN이다.
- [ ] 정상 서명의 만료 토큰은 401 TOKEN_EXPIRED이다.
- [ ] 검증된 sub에 해당하는 실제 계정을 확인하고 그 ID만 전달한다.
- [ ] 보호 API의 401에 WWW-Authenticate: Bearer를 포함한다.
- [ ] /me가 Alice와 Bob 각각의 id·name·email을 200으로 반환한다.
- [ ] 공개 GET 목록·상세는 로그인 없이 200으로 조회된다.

## 4 BE-03 권한과 입력 검증

- [ ] 등록 시 작성자를 요청 본문이 아닌 검증된 사용자 ID로 저장한다.
- [ ] assertOwner / assert_owner가 로그인 사용자와 DB의 authorId를 비교한다.
- [ ] 타인 글 수정·삭제는 403 FORBIDDEN이며 DB를 변경하지 않는다.
- [ ] 본인 수정은 200이며 작성자와 createdAt은 유지된다.
- [ ] 본인 삭제는 204이며 JSON·문자열·null을 포함한 응답 본문이 없다.
- [ ] 등록은 201이며 Location: /api/posts/{id}가 있다.
- [ ] 제목·내용 필수, 문자열, 공백, 1~100자·1~5000자를 서버에서 검사한다.
- [ ] 등록·수정에 authorId·userId·id 등 추가 필드는 400 BAD_INPUT이다.
- [ ] 잘못된 ID는 400, 정상 ID의 없는 글은 404 NOT_FOUND이다.
- [ ] 정상 형식의 보호 요청은 인증 → 글 존재 → 권한 → 입력 → 변경 순서이다.
- [ ] 거부된 요청 후 공개 조회해 데이터가 변경되지 않았는지 확인했다.

## 5 FE-01 로그인 상태

React/Vue 모두 src/api.js의 FE-01~04를 수정합니다. 화면은 React src/main.jsx, Vue src/App.vue입니다.

- [ ] 로그인 폼의 email·password를 JSON으로 API에 전송한다.
- [ ] 성공 후 accessToken과 user를 메모리에 저장하고 화면을 갱신한다.
- [ ] 로그인 실패 시 성공 표시를 하지 않고 오류를 보여 준다.
- [ ] localStorage·sessionStorage에 토큰을 저장하지 않는다.
- [ ] 로그인 사용자 이름, 비로그인 안내, 로그아웃 버튼 상태가 맞다.

## 6 FE-02 토큰 전송과 FE-03 오류 처리

- [ ] authorizationHeaders가 Authorization: Bearer <JWT>를 만든다.
- [ ] Network에서 /me·등록·수정·삭제의 실제 헤더를 확인했다.
- [ ] 토큰이 없을 때 Bearer undefined 같은 잘못된 값을 만들지 않는다.
- [ ] 204 삭제 응답을 JSON으로 파싱하지 않는다.
- [ ] 400은 입력 수정 안내, 401은 상태 해제와 재로그인 안내로 처리한다.
- [ ] 401의 INVALID_CREDENTIALS·TOKEN_REQUIRED·INVALID_TOKEN·TOKEN_EXPIRED를 구분해 안내한다.
- [ ] 403은 권한 부족 안내이며 로그인 상태를 자동 해제하지 않는다.
- [ ] 404는 글 없음 안내와 목록 복귀 또는 갱신을 제공한다.
- [ ] 요청 실패를 성공 알림이나 정상 저장으로 표시하지 않는다.

## 7 FE-04 버튼과 데이터 유지

- [ ] canEdit가 로그인 사용자와 글 작성자를 비교한다.
- [ ] 비로그인 사용자에게 글 작성 시 로그인 안내를 표시한다.
- [ ] 타인의 수정·삭제 버튼을 숨기거나 비활성화한다.
- [ ] 로그아웃 즉시 메모리 상태·로그인 표시·버튼이 갱신된다.
- [ ] 새로고침 후 글은 남고 로그인 상태는 해제된다.
- [ ] 백엔드를 실제 종료·재실행해 글과 작성자·내용이 유지된다.
- [ ] 최종 화면의 인증 미완성 데모 배너를 교체했다.

## 8 HTTP 응답과 수동 테스트

- [ ] 성공 상태 200·201·204를 명세대로 구분했다.
- [ ] 실패 상태 400·401·403·404와 JSON code가 각각 정확하다.
- [ ] 오류 본문은 code·message이며, HTTP 200 본문에 오류만 넣지 않는다.
- [ ] 지정 API에 기본 422, HTML 로그인 이동, 예상 가능한 오류의 500이 남지 않는다.
- [ ] T01~T17을 모두 수행하고 예상·실제 HTTP, code, 응답 헤더, 화면, 증거를 기록했다.
- [ ] 타인 글 변경을 UI 버튼이 아닌 직접 API 요청으로도 시험했다.
- [ ] 토큰 누락·변조·만료를 서로 다른 조건으로 검사했다.
- [ ] 토큰 없이 없는 글 수정은 401, 정상 토큰으로 없는 글 수정은 404이다.
- [ ] Bob의 정상 토큰으로 Alice 글의 잘못된 입력 수정은 403이다.
- [ ] 자동 final 검사와 수동 UI·재시작 검사를 구분했다.
