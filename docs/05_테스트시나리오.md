# 최종 제출본 테스트 시나리오

최종 검증은 `07_로컬실행안내.md`에 따라 백엔드를 실행하고, 프론트에서 `npm run build`와 `npm run preview`를 실행한 뒤 http://127.0.0.1:4173 에서 진행합니다. 새 폴더 설치, 빌드 성공 로그, 접속 주소와 API 요청이 보이는 화면을 보고서에 포함하세요.

두 계정은 Alice(id 1), Bob(id 2)이며 공통 비밀번호는 Classroom!2026입니다. 개발자 도구 Network, API 클라이언트 또는 curl로 서버 응답을 확인합니다. 프론트 버튼이 숨겨져 있어도 서버에 직접 요청해 권한을 확인해야 합니다.

| ID | 절차 | 기대 결과 |
|---|---|---|
| T01 | 토큰 없이 목록 및 존재하는 글 상세 조회 | 200, 정상 공개 조회 |
| T02 | Alice 계정으로 로그인 | 200, JWT와 공개 사용자 정보, 화면 로그인 표시 |
| T03 | 잘못된 비밀번호 및 없는 이메일로 각각 로그인 | 401 INVALID_CREDENTIALS, 토큰 미발급 |
| T04 | 토큰 없이 /me와 글 등록 요청 | 각각 401 TOKEN_REQUIRED |
| T05 | Alice 토큰으로 글 작성 후 /me 조회 | 201, authorId 1, /me는 Alice |
| T06 | Alice 토큰으로 본인 글 수정·삭제 | 200 및 204, 결과가 DB에 반영 |
| T07 | Alice 글을 Bob의 정상 토큰으로 수정 | 403 FORBIDDEN, 원문 유지 |
| T08 | Alice 글을 Bob의 정상 토큰으로 삭제 | 403 FORBIDDEN, 글 유지 |
| T09 | 유효 토큰의 서명 부분 첫 글자를 다른 문자로 바꿔 /me 및 변경 요청 | 401 INVALID_TOKEN, 데이터 변경 없음 |
| T10 | 짧은 TTL로 발급하고 실제 만료 뒤 /me 및 변경 요청 | 401 TOKEN_EXPIRED, 화면 로그인 해제와 안내 |
| T11 | 로그인 후 로그아웃, 다음 /me 요청 | 헤더에서 토큰이 빠지고 401 TOKEN_REQUIRED |
| T12 | Bob 로그인 상태로 글 등록 요청에 authorId:1 또는 userId:1 추가 | 400 BAD_INPUT, 위조 글 미생성 |
| T13 | 본인 토큰으로 빈 제목·공백 본문·길이 초과 입력을 각각 전송 | 400 BAD_INPUT, DB 변경 없음 |
| T14 | 없는 양의 정수 ID의 조회·수정·삭제 및 잘못된 ID 조회 | 없는 글 404, 잘못된 ID 400; 수정·삭제에는 정상 토큰 사용 |
| T15 | 글을 만든 뒤 서버 종료·재실행 | 기존 글과 작성자·내용 유지 |
| T16 | 로그인 후 페이지 새로고침 | 공개 글 유지, 메모리 로그인 상태 해제 |
| T17 | 토큰 없는 수정·삭제 요청과 Bob 계정의 정상 작성·본인 수정·삭제 | 무토큰은 401, Bob 본인 작업은 성공 |

T07~T09는 각각 실패 응답 후 공개 조회로 데이터가 바뀌지 않았음을 확인합니다. T09의 변경 요청에는 POST, PUT, DELETE를 포함합니다. T10의 만료 요청도 /me뿐 아니라 게시글 변경 API에서 확인하세요. T12는 authorId와 userId를 각각 검사합니다. T15는 검사 스크립트를 다시 실행하는 것으로 대체하지 말고 실제 서버 프로세스를 재시작합니다.

테스트 증거에는 ID, 요청 메서드·URL, 사용자, HTTP 상태, 실제 결과, 캡처 또는 로그를 포함합니다. 토큰 원문과 비밀 키는 가립니다. 재현용 명령에는 실제 JWT 대신 <TOKEN>을 사용합니다.

추가로 잘못된 알고리즘, iss/aud 불일치, exp/sub 누락이 거부되는지 점검하면 좋습니다. 이를 위해 JWT를 조작할 경우 본인의 로컬 실습 키와 서버만 사용합니다. 단순히 payload를 바꾸면 서명 실패를 검사하는 것이므로 클레임 검사를 따로 확인한 것으로 기록하면 안 됩니다.

## 응답 코드를 확인하는 절차

1. Network 또는 API 클라이언트에서 실제 HTTP 상태를 확인합니다. 성공 200·201·204를 구분하고, 실패 시 JSON code·message도 확인합니다.
2. 등록 201의 Location, 보호 API 401의 WWW-Authenticate: Bearer, 삭제 204의 빈 본문을 각각 기록합니다.
3. 보고서에는 요청 메서드·URL, 사용자와 토큰 조건, 요청 본문, 예상 HTTP/code, 실제 HTTP/code, 필요한 응답 헤더, 화면 변화, 증거 파일명을 남깁니다. 실제 JWT와 비밀 키는 가립니다.
4. UI에서 버튼을 숨겼더라도 Bob의 토큰으로 직접 변경 요청을 보내 403을 확인합니다. 해당 실패 뒤 글을 다시 조회해 내용이 유지됨을 확인합니다.
5. 401이면 로그인 상태가 해제되고, 403이면 로그인 상태가 유지되는지 확인합니다. 204는 JSON 파싱 오류 없이 삭제 화면을 갱신해야 합니다.

## 여러 오류 조건이 겹칠 때

정상 JSON과 정상 형식의 ID를 사용합니다. 토큰 없이 없는 글을 수정하면 401 TOKEN_REQUIRED, 정상 토큰으로 같은 글을 수정하면 404 NOT_FOUND입니다. Bob이 Alice 글에 공백 제목을 보내면 권한 검사에서 403 FORBIDDEN, Alice가 자기 글에 같은 입력을 보내면 400 BAD_INPUT입니다. Bob의 토큰이 만료되었다면 권한 검사 전에 401 TOKEN_EXPIRED입니다. 실제 응답을 보고서의 HTTP 확인 기록에 추가하세요.
